# Mantralayam Guest Booking Workflow

## Objective
Let pilgrims search room availability, book rooms, look up and cancel their own bookings online, against the existing Mantralayam database, without ever double-booking a room.

## Status
| Part | State |
|------|-------|
| Guest website `web/guest.html` (+ `shared.css`, `tokens.css`) | done, served at `/` |
| Public API (`/api/public/*`) in `tools/mantralayam_rooms.py` | done, tested |
| Staff app and staff API (login, check-in/out, room status, properties, users, audit view, `/staff`) | **not rebuilt**: the original source was lost; only its data remains in the database |
| Real property photos | optional, not built (guest page shows "Photo coming soon") |
| Export report to Google Sheets | not built, needs `credentials.json` |

## Inputs and data
- Database: `.tmp/mantralayam.db` (override with env `MANTRALAYAM_DB`). Tables: `properties`, `room_types`, `rooms`, `bookings`, `room_status_events`, `settings`, `audit_log`, `users`, `roles`, `user_properties`. The tool never reseeds data; `migrate()` only adds missing columns or tables (currently `room_types.active`, `bookings.arrival_time`, `bookings.darshan_date` and the tables `holds`, `peak_periods` and `callback_requests`), once per process and database file.
- Settings (table `settings`, defaults in the tool): `guest_booking_enabled`, `guest_max_rooms` (3), `guest_advance_days` (90), `guest_max_nights` (15), `guest_cancel_cutoff_hours` (24), `checkin_time` (14:00), `checkout_time` (11:00).

## How to run
```
python tools/mantralayam_rooms.py serve [PORT]     # http://127.0.0.1:8001
python tools/run_all.py                            # guest (8001) and staff (8002) together
python tools/mantralayam_rooms.py backup           # verified DB copy in backups/, newest 14 kept; exit code 1 + message on failure (schedule daily, see below)
python tools/test_mantralayam_rooms.py             # prints "ok"; runs on a COPY of the database
```

## API (all JSON)
| Method and path | Purpose |
|---|---|
| GET/HEAD `/health` | uptime check: 200 `{"status":"ok","checks":{...}}`, or 503 when the database or the newest backup is bad (see Production hardening) |
| GET `/images/<file>` | any png/jpg/webp/svg/ico in `web/images/` (no allowlist to edit; other types and path tricks give 404) |
| GET `/api/public/info` | properties, room types, settings, today, upcoming active `peak_periods` |
| GET `/api/public/search?check_in&check_out&guests[&property_id&room_type_id]` | free room types grouped by property, with rooms needed for the party |
| POST `/api/public/hold` `{property_id, room_type_id, rooms, check_in, check_out[, token]}` | holds the rooms for 10 minutes; returns `{token, expires_at, seconds, rooms}`. Passing the previous `token` replaces that hold |
| POST `/api/public/release` `{token}` | frees a hold at once |
| POST `/api/public/book` | creates a booking (1 to 3 rooms of one type); optional `hold_token` books the held rooms; a filled `website` field (honeypot) is refused; returns the booking view |
| POST `/api/public/booking/lookup` `{booking_id, phone}` | view a booking |
| POST `/api/public/booking/cancel` `{booking_id, phone, reason}` | cancel before the cutoff |
| GET `/api/public/calendar?month=YYYY-MM` | colour-coded availability and per-night prices |
| POST `/api/public/quote` | price breakdown before confirming |
| POST `/api/public/booking/change` | change the dates of a booking (preview, then `confirm`) |
| POST `/api/public/waitlist`, `/waitlist/cancel` | "notify me" for sold-out dates |
| POST `/api/public/otp/send`, `/otp/verify` | SMS code for a booking or a My bookings sign-in |
| `/api/me/*` | signed-in guest (cookie + CSRF header): session, bookings, receipt, cancel, change, update, profile, logout |

Errors return `{"error": "<message for the guest>"}` with 400, 403 (online booking off), 404, 409 (room taken, cannot cancel), 429 (rate limit) or 5xx. A 429 also carries `retry_after` (seconds) in the body and as the `Retry-After` header, and the message says how long to wait.

## Rules
- A room is free for `[check_in, check_out)` if it and its property are active, no `Confirmed` or `Checked-In` booking overlaps, and no active `room_status_event` overlaps (open-ended events block indefinitely). Same-day turnover is allowed.
- Cleaning events (`cleaning_required`, `in_cleaning`) only block stays starting today or earlier. This is inferred, confirm with property staff.
- The availability check and the insert run in one `BEGIN IMMEDIATE` transaction.
- Multi-room bookings create one row per room, sharing `group_id`, which is the booking ID shown to the guest. Guests are spread evenly, at least one per room, none above room capacity.
- Online bookings are `source='online'`, `payment_method='pay_at_counter'`, `payment_status='due'`; `amount` is the grand total from `quote()` (room charge, extras, discount, tax), nothing is charged online.
- Booking ID plus mobile number (last 10 digits compared) is the credential for lookup, cancel and date change without signing in; the booking itself needs an SMS-verified mobile number. My bookings uses the verified number instead.
- Cancelling is allowed while status is `Confirmed` and now is before check-in time minus the cutoff hours. Cancellation reason is mandatory.
- Every online create and cancel writes an `audit_log` row (`booking.online_create`, `booking.online_cancel`, user `guest`).
- Rate limits (stored in the database, kept across restarts) per IP: 60 searches per minute, 10 hold requests and 10 booking attempts per 10 minutes, 20 lookups, cancels or date changes per 10 minutes; plus 5 bookings per 10 minutes per mobile number. OTP, promo and waiting-list limits are listed under Production hardening.
- Holds: table `holds` (token, room, dates, `expires_at`, ip). `free_rooms()` treats an unexpired hold as unavailable to everyone except the holder's own token, so the booking transaction (`BEGIN IMMEDIATE`) still decides every race and double-booking stays impossible. Expired rows are ignored by the query and swept on the next hold; no background job. One IP may keep at most 3 live holds (429 after that). The guest page takes the hold when the confirm dialog opens, shows a countdown, re-holds when the room count changes, releases on close or page exit, and the booking consumes it. Staff walk-in booking is refused for a held room with a message saying it is held until HH:MM.
- Honeypot: the hidden, `inert` field `website` in the booking form. A bot that fills it gets a generic 400, counts double against its IP limit, and no booking is created.

## Edge cases
- Dates: valid ISO, not in the past, check-out after check-in, within the advance window and night limit.
- Phone 10 to 13 digits; ID type from a fixed list; email optional but validated.
- Two guests racing for the last room: the second gets 409 "no longer available" and the page re-runs the search.
- Wrong booking ID or wrong phone give the same 404 message, so IDs cannot be probed.

## Known limits
- The apps listen on 127.0.0.1 only; HTTPS comes from the reverse proxy (`docs/DEPLOYMENT.md`). No online payment: the advance shown in the price breakdown is informational. The Telugu, Kannada, Tamil and Hindi texts (including the new SMS and receipt texts) are `TODO` and fall back to English.
- Server clock is used for "today" and cancel deadlines; it must be set to India time.
- Staff features are missing (see Status).

## Lessons learned
- 2026-10-06: `guest.html` linked only `shared.css`, so all `var(--...)` colors from `tokens.css` were undefined and the page was unstyled. Fixed by linking `tokens.css` first.
- 2026-10-06: `replaceChildren(array)` stringifies the array (`[object HTMLDivElement]`); spread it instead.
- Seed data: the "Non-AC Double" rooms list "AC" among their amenities. That is a data issue in `rooms.amenities`, not a code issue.
- 2026-10-28: images were served from a hard-coded allowlist, so a new banner 404'd until the list was edited. Now any image file in `web/images/` is served. The rooms test used to assert the real DB had zero online bookings; real ones exist, so it now checks the count is unchanged. The `.venv` points to a missing Python 3.14; use Python 3.12 (`py -3.12`).
- Peak periods (table `peak_periods`: name, start_date, end_date, optional max_nights, max_rooms, note, active). A period's end date is its last night, so a stay touches it when `start_date < check_out` and `end_date >= check_in`. `parse_stay()` tightens `max_nights` and `max_rooms` to the strictest overlapping active period (a period can only tighten the normal settings, never loosen them), so search, hold and book all enforce the same limits; refusals name the period, for example "During Brahmotsavam online bookings can be for at most 2 nights". The search response includes `peak` (the periods for the searched dates, with notes) and `info.peak_periods` lets the form show the note while the guest is still picking dates, in the results and in the confirm dialog. Existing bookings are never changed by a new period. Managed on the staff Admin page (super_admin only), see `workflows/mantralayam_staff.md`.
- 2026-10-28 lesson: `migrate()` runs once per process per database path. Replacing the database file under a running server (as a UI test harness does) leaves the new copy without the new tables until the server restarts.

## Backup and restore (added 2026-10-28)
`backup` uses SQLite's online backup API, so it is safe while both servers run. It writes `backups/mantralayam-YYYY-MM-DD-HHMM.db` (folder is gitignored; override with env `MANTRALAYAM_BACKUPS`), runs `PRAGMA integrity_check` on the copy, and only then deletes everything but the newest 14 (`mantralayam-????-??-??-????.db` only; other files are never touched). A failed run deletes its partial copy, rotates nothing, prints `Backup FAILED: <reason>` to stderr and exits 1. Every run appends `time<TAB>OK|FAILED<TAB>detail` to `backups/backup.log`; the staff Dashboard shows the last line as "Last backup: ... OK/FAILED" to super_admin only (nothing real shows until the first run). Two runs in the same minute replace each other.

Schedule it daily at 02:00 (run once in Command Prompt; use the full path of `python.exe`, here Python 3.12):
```
schtasks /Create /SC DAILY /ST 02:00 /TN "Mantralayam Backup" /TR "\"C:\Users\keerthana\AppData\Local\Programs\Python\Python312\python.exe\" \"C:\Users\keerthana\Desktop\claude\tools\mantralayam_rooms.py\" backup"
schtasks /Run /TN "Mantralayam Backup"
schtasks /Query /TN "Mantralayam Backup" /V /FO LIST
```
`/Run` tries it now (then check `backups\backup.log`); in the query output "Last Result: 0" means the last run succeeded. The task runs only while the PC is on and the user is logged in (add `/RU SYSTEM` from an administrator prompt to avoid that). If the PC was off at 02:00 the dashboard line goes stale, so check its date.

Restore: stop both servers (Ctrl+C in the `run_all.py` window); keep the current file (`copy .tmp\mantralayam.db .tmp\mantralayam.before-restore.db`); delete `.tmp\mantralayam.db-wal` and `-shm` if present; copy the chosen `backups\mantralayam-....db` over `.tmp\mantralayam.db`; start the servers. Bookings made after that backup are lost, so tell staff what time the data goes back to. Staff accounts come back as of the backup too.

## Date flexibility on sold-out searches (added 2026-10-28)
`alternatives(conn, ci, co, guests, property_ids=None, type_id=None, max_rooms=None)` in `mantralayam_rooms.py` is the one shared function. For a sold-out request it tries check-in dates 1 to 14 days either side (same number of nights), nearest first (earlier before later on a tie), and returns the first 3 that are bookable: each candidate passes `check_stay()` (the date rules split out of `parse_stay`: not in the past, `guest_advance_days`, `guest_max_nights` including peak-period limits) and `free_rooms()` has rooms that cover the party within the room limit (`max_rooms`, default the online limit). Each result is `{check_in, check_out, nights, days_away}`. Up to 28 small queries per call.
- `/api/public/search` always includes `alternatives` (empty unless the search found nothing, then up to 3; the search's property and room-type filters are kept). `guest.html` shows buttons "2 nights free from 5 Nov" that fill the dates and search again.
- Not offered: a party that needs more than the online room limit (no date helps), stays longer than the night limit, dates past the advance window, anything in the past.
- Staff use the same function through `GET /api/availability` (see `workflows/mantralayam_staff.md`).

## Call-back requests (added 2026-10-28)
Table `callback_requests` (created by `migrate()`): `id, property_id (nullable), name, phone, people, check_in, check_out, note, status new|contacted|closed, created_at, handled_by, handled_at`.
- `POST /api/public/callback {name, phone, people, check_in, check_out[, note, property_id]}` returns `{"ok": true}`. Every field is validated on the server: name 1-100 characters, phone 10-13 digits, people 1-500, dates valid, not in the past, check-out after check-in, check-in within 366 days and at most 60 nights, note up to 500 characters, property (optional) must be active. The hidden `website` field is a honeypot (filled: generic 400, counts double against the IP, nothing stored). Rate limit uses the same `throttle()` helper as booking but its own counters: 5 requests per 10 minutes per IP and 3 per mobile number (429 with `retry_after` and the `Retry-After` header). Each request is audited as `callback.request` (user `guest`).
- `/api/public/search` adds `callback`: `"group"` (rooms are free but the party needs more rooms than may be booked online), `"soldout"` (nothing free and no alternative dates) or `null`. `guest.html` shows the "Request a call-back" form under the results for the first two, with the search's dates and party size filled in and the search's property (if one was chosen) attached.
- Known limit: someone rotating IP addresses and phone numbers could still fill the staff queue; staff can close junk requests. Nothing is emailed or texted, staff see requests only on the Call-backs page.

## Arrival details on bookings (added 2026-10-28)
Two optional columns on `bookings`, added by `migrate()` (existing rows stay NULL): `arrival_time` (text `HH:MM`, 00:00 to 23:59) and `darshan_date` (ISO date, today or later; it does not have to fall inside the stay). They are separate from the existing 500-character note (`bookings.remarks`, "Special requests" for guests), which is unchanged; there is no second note field. `arrival_fields()` in `mantralayam_rooms.py` validates both for the guest and staff paths (bad time: "Expected arrival time must look like 14:30."; past or invalid date: refused; empty means not given). The guest booking form has "Expected arrival time" and "Darshan date"; the confirm dialog summary echoes them as they are typed, and the booking view (confirmation page and My booking) shows them next to the requests. A group booking stores them on every room row. All text from guests is put on the page as text (the pages never use `innerHTML`; a test checks this), so `<b>` in a note shows as typed.

## Production hardening (added 2026-11-01)
Deployment steps, DNS, proxy configs and the monitor setup are in `docs/DEPLOYMENT.md`; the proxy and service files are in `deploy/`.
- **HTTPS.** Both apps still listen on 127.0.0.1 only. A reverse proxy (Caddy with automatic TLS, or nginx + certbot) terminates HTTPS. `MANTRALAYAM_HTTPS=1` adds `Secure` to the cookies (staff `staff_session`, guest `guest_session`, both HttpOnly and SameSite=Strict) and sends `Strict-Transport-Security` (1 year, includeSubDomains, no preload). `TRUST_PROXY=1` reads `X-Forwarded-For` (from the right: the first address that is not a trusted proxy, `TRUSTED_PROXIES`) and `X-Forwarded-Proto`. `ALLOWED_HOSTS` restricts the Host header. With `MANTRALAYAM_HTTPS=1` the guest app refuses to start with `SMS_PROVIDER=mock` while OTP is required, and never sends a code through the mock.
- **Rate limits are in the database** (`rate_hits (key, ts)`), shared by both servers and kept across restarts. `throttle()` (and `rate()` for staff, which counts login failures only and clears them on success) opens its own short connection: never call it inside `write()`. Limits are unchanged, plus: 10 OTP codes per hour per device, 5 per hour and one per 30 s per mobile number, 30 OTP checks per 10 minutes per device, 15 wrong promo codes per 10 minutes per device, 5 waiting-list requests per 10 minutes per device. `reset_throttle()` clears the counters (tests).
- **`GET /health`** (also `HEAD`, on both servers): `200 {"status":"ok","checks":{"database":"ok","backup":"ok","backup_age_hours":3.2}}`, or `503 {"status":"fail", ...}` when the database cannot be read or the newest backup run failed (`failed`), is older than `HEALTH_BACKUP_MAX_HOURS` (`stale`, default 30) or never ran (`none`). `HEALTH_BACKUP_MAX_HOURS=0` skips the backup check. No paths or error text are returned.
- **Alerts** (table `alerts (kind, key, message, created_at, resolved_at, emailed_at, email_note)`). `check_alerts()` opens, refreshes or resolves: `backup/status` (failed, stale or none), `holds/pressure` (at least 3 rooms and `HOLD_ALERT_PERCENT` % of active rooms on an unexpired hold at once: unpaid reservations locking rooms) and `holds/lapsed` (`HOLD_LAPSE_ALERT` or more holds expired unbooked in the last hour). A new alert is emailed once to `STAFF_ALERT_EMAILS` (provider interface in `tools/providers.py`; no address configured: dashboard only, and the alert says so). The staff dashboard shows open alerts as a red banner to super admins and property managers (`alerts` in `GET /api/dashboard`; opening the dashboard also runs the check). `backup()` opens or clears the backup alert at once. `python tools/mantralayam_rooms.py tick` (every 5 minutes: `deploy/mantralayam-tick.timer`, or `run_all.py` in development) runs `check_alerts()`, `waitlist_tick()` and pings `HEARTBEAT_URL`. Lapsed holds are kept for a day (the per-IP hold cap counts only unexpired ones).
- **CSRF.** The staff reply to login and `GET /api/meta` carries `csrf` (derived from the session token); the staff page sends it as `X-CSRF-Token` on every POST and the handler rejects a signed-in POST without it (`dispatch(..., check_csrf=True)`; plain dispatch calls in tests skip the check). Guest `/api/me/*` POSTs work the same. All POSTs also need `Content-Type: application/json`, and a browser `Origin` that is not this site gets 403.
- **Headers and input.** Every response carries CSP (script/style/font/frame allow-lists, `frame-ancestors 'none'`, `base-uri`, `form-action`), `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options: DENY`, `Permissions-Policy`, `Cross-Origin-Opener-Policy` (+ HSTS over HTTPS). `clean_body()` checks every JSON body (and query): only objects, lists, text, numbers, booleans and null, at most 4 deep, 60 keys or items per level, 2000 characters per text (query values 200), control characters removed; bodies over 20 000 bytes get 413.
- **Optional CAPTCHA** (`CAPTCHA_PROVIDER=turnstile|mock`, off by default): `captcha_token` is required on OTP requests, Call me back and call-back forms and the waiting list, besides the honeypot. When OTP is required, booking itself is not CAPTCHA-checked (the code is the check). Fails closed. `info` returns `captcha: {provider, site_key}`; the page renders the widget and the CSP allows Cloudflare Turnstile only while it is enabled.

## Booking-flow upgrade (added 2026-11-01)
- **Calendar.** `GET /api/public/calendar?month=YYYY-MM[&property_id&room_type_id&senior&ground_floor]` returns one entry per day: `status` (`available`, `few` = 2 or fewer rooms, `soldout`, `closed` = past or beyond the advance window), `free`, the lowest nightly `price` for that night (peak surcharge included) and the `peak` period name. The page colours each day and also shows a symbol and text (not colour alone), and lets the guest pick check-in then check-out.
- **Nightly prices and peak surcharge.** `peak_periods.surcharge_percent` (optional, admin) raises the tariff on those nights; a night in several periods takes the largest. `night_prices()` is the one function; search totals, the calendar, the quote and the booking all use it.
- **Price breakdown.** `POST /api/public/quote` takes the booking inputs (plus optional `children`, `extra_beds`, `promo_code`, `phone`) and returns nights with prices, room charge, extra beds, children, discount, subtotal, tax, total, advance and balance. `book()` calls the same `quote()` inside its transaction and stores the result: grand total in `bookings.amount` (split to the paisa over the rooms), `tax_amount`, `discount_amount`, `advance_due`, `promo_code`, `children`, `extra_beds`, and the whole breakdown as JSON in `price_json` of the first row. Order: room charge + extra beds + children = subtotal; discount comes off the room charge only; tax on the rest; advance is a percentage of the total. Nothing is collected online: the advance is informational (the property collects it).
- **Pricing rules (settings, all empty = not charged)**: `tax_percent`, `advance_percent`, `extra_bed_price` (per bed per night; `extra_bed_max` per room, default 1), `child_price` (per child per night), `child_counts_capacity` (default on: children use room capacity; off: they share existing beds). Admin > Settings. No rates are assumed: the owner must decide them (including the correct GST treatment of the room tariffs).
- **Filters.** `rooms.senior_friendly` (admin flag per room) and ground floor (`rooms.floor = 0`) become `senior=1` / `ground_floor=1` on search, calendar, hold, quote, book and the waiting list. The booking lands only on rooms that match. `info.filters` says whether any such room exists, so the page shows only filters that can match.
- **Booking on behalf.** `guest_name` is the person staying; optional `booker_name`, `arrival_contact_name` and `arrival_contact_phone` (columns on `bookings`). `phone` is the booker's verified mobile and is the key for lookup, OTP and My bookings. Staff see all three in the booking tables.
- **Promo, donor and group-rate codes** (`promo_codes`, Admin > Promo codes): `code` (any case; empty for an automatic group rate with `auto`), percent or flat rupees off the room charge, optional cap, minimum rooms/guests/nights, valid-from/until (booking date), total and per-mobile usage limits (counted from bookings that are not cancelled, so a cancellation gives the use back), building/room-type scope and `exclude_peak` (default: not on peak dates). One discount per booking: the larger of the typed code and the best qualifying automatic rate. A bad code raises a specific error and never blocks the price on the page. Guessing is throttled.
- **Date change.** `POST /api/public/booking/change {booking_id, phone, check_in, check_out[, confirm]}` (and `/api/me/booking/change`). Without `confirm` it only returns the old and new totals and what would move; with `confirm: true` it applies in one transaction. Allowed while the booking is Confirmed, before the cancellation cutoff, with nothing recorded as paid, and the new stay passing the normal online rules. Each room keeps its room if free on the new dates, otherwise another free room of the same type and building; it is repriced with the stored party and code (dropped, with a notice, if no longer valid, for example on peak dates). Audited as `booking.online_change_dates`. Staff reschedule still sets amount = tariff x nights and clears the online breakdown.
- **Waiting list.** `POST /api/public/waitlist {name, phone, email?, check_in, check_out, guests, property_id?, room_type_id?, senior?, ground_floor?, lang}` is accepted only while nothing bookable is free for those dates (the search says `waitlist: true`); at most 3 open requests per mobile number. `waitlist_tick()` (after every guest or staff cancellation, a released block or a reschedule, and in the 5-minute job) expires past requests and, oldest first, SMS (and email) a guest once when their stay is bookable again, without promising the same rooms twice (requests notified in the last 3 hours count against the free rooms). Nothing is reserved. Booking the dates closes the request. `POST /api/public/waitlist/cancel {id, phone}`.

## Phone OTP, My bookings, saved details (added 2026-11-01)
- **OTP.** `POST /api/public/otp/send {phone, purpose: booking|login, lang?, captcha_token?}` sends a 6-digit code through the SMS provider interface (`tools/providers.py`: `SMS_PROVIDER=mock` prints it to the console in development, `http` posts to a gateway; the text is `sms.otp` in `web/locales`). Codes live 5 minutes, allow 5 wrong tries, are stored as a salted HMAC, are replaced by a newer code, and never appear in logs or the audit log. `POST /api/public/otp/verify {phone, purpose, code}` returns, for `booking`, a one-use `proof` (valid 15 minutes, tied to that mobile number) plus the saved details if the guest opted in; for `login` it starts a session. `book()` requires `otp_proof` unless `BOOKING_OTP_REQUIRED=0`; the proof is consumed inside the booking transaction, so a failed attempt keeps it. A `login` request for a number with no bookings or saved details answers the same and sends nothing.
- **My bookings** (`#/account`). Session cookie `guest_session` (24 hours; only a hash is stored in `guest_sessions`), CSRF header on POSTs. Routes: `GET /api/me/session`, `GET /api/me/bookings` (online bookings for that mobile number, newest first, plus open waiting-list requests and saved details), `GET /api/me/receipt?booking_id=` (a printable HTML receipt, downloaded as a file; save as PDF from the print dialog; not a tax invoice), `POST /api/me/booking/cancel`, `/change`, `/update` (arrival time, darshan date, special requests, arrival contact), `/api/me/profile/delete`, `/api/me/waitlist/cancel`, `/api/me/logout`. Lookup by booking ID + mobile (`#/booking`) still works without signing in.
- **Saved details** (`guest_profiles`: name, email, ID type, consent time). Only saved when the guest ticks the box (unchecked by default) on a booking whose mobile number was verified. The ID number is never stored. Guests can delete them in My bookings.
- Staff cancel, reschedule and release actions call `waitlist_tick_safe()` after committing.

## Notifications, receipts and payments (added 2026-11-02)
- **Messages** (`tools/notifications.py`): on confirmation, change and cancellation of an online booking (guest or staff action) an SMS, a WhatsApp message (only when `WHATSAPP_PROVIDER` is set) and an email go out in the booking's language (`bookings.lang`; `TODO` translations fall back to English). The email is HTML with an inline QR code (check-in code `MR1.<id>.<signature>`, an HMAC with a server secret) and the PDF receipt attached. `notification_log` keeps channel, masked recipient, status and error class only, never text, IDs or codes. `tick` retries failed sends (3 tries in 24 h) and sends the arrival reminder once (`reminder_days`, `reminder_hour`; empty days = off).
- **PDF** (`tools/pdfdoc.py`, `tools/qr.py`, stdlib): English only, because the standard PDF fonts cannot show Indian scripts; the HTML receipt and email use the guest's language. `POST /api/public/booking/receipt` (ID + mobile) and `GET /api/me/receipt.pdf`.
- **Payments** (`tools/payments.py`): options `full`, `advance` (advance_percent), `counter`, chosen in Admin > Settings; online ones need `PAYMENT_PROVIDER`. `book()` with an online option only starts a payment: it extends the room hold to 15 minutes, creates the provider order and stores a `payments` row with the booking details sealed (`tools/idvault.py`). The booking is created when the payment is confirmed, by the checkout success call (`/api/public/payment/verify`, signature checked) or the webhook (`/api/public/payment/webhook`, signature over the raw body, each event id once). `captured()` is idempotent. Abandoned or unpaid payments let the hold lapse and `tick` marks them expired; a capture that arrives after the rooms went is refunded in full (`unfulfilled`). Card data never reaches the server.
- **Refunds**: a cancellation (guest, or a staff manager) records a refund of `refund_percent` of the money held for the cancelled rooms; `refunds` rows move requested -> pending -> processed (provider webhook), or `failed` after 5 tries, or `manual` when no policy is set or the money was taken at the counter. Each is sent once (claimed first; the provider gets the refund's receipt as idempotency key). One staff alert covers every refund that needs a person.
- **Reconciliation**: `payments` (online and counter) and `refunds` against bookings: `bookings.payment_status` is due, partial, paid, refunded or partially_refunded; Staff > Payments flags unpaid balances, overpayments, open refunds and money held after a cancellation.
- Edge cases: the provider's checkout and webhook may arrive in either order; a second webhook with the same event id does nothing; a bad signature changes nothing; a mismatching amount is refunded, not booked; the mock checkout does not exist over HTTPS.
- Overlap guard: a database trigger refuses any second live (Confirmed or Checked-In) booking that overlaps in a room, whatever code writes it.

## Sevas, festivals, notices, feedback, broadcasts, PWA (added 2026-11-02)
- **Sevas** (`tools/extras.py`): `sevas` (price, places per day) and `packages` (named sevas on fixed days of the stay, a discount on them, minimum nights) are set in Admin. The quote adds the seva lines after tax: not taxed, not discounted by promo codes, included in the advance and the refund base. Capacity is shown at quote time and checked again inside the booking transaction; a paid booking whose seva filled meanwhile is refunded like a lost room. `seva_bookings` follow the stay (cancelled with it). Online and staff date changes are refused for a booking with sevas.
- **Festivals and panchanga**: entered by staff, never calculated. A festival can own a peak period (surcharge, night and room limits), so prices, the calendar and limits follow it; deactivating the festival switches the peak period off. `GET /api/public/festivals` and the home page list upcoming ones.
- **Notices** (weather, river level; info, watch, warning): shown at the top of the guest site; a stay's confirmation (email, booking page, printable receipt) lists those covering its dates, and a warning also goes in the SMS. Text is whatever staff write; nothing is fetched.
- **Feedback**: `tick` asks each online guest once, `feedback_days` after check-out (empty = off), with a signed link (`FB1.<id>.<sig>`). One rating per stay (1 to 5, optional cleanliness and service, comment). A rating of 1 or 2 raises a staff alert until reviewed in Staff > Feedback.
- **Broadcasts**: opt-in on the guest site (consent box; SMS or WhatsApp need a number verified by an SMS code, email needs a click on the link we send). Staff > Broadcasts sends to opted-in people only, in their language (English fallback), each message with an unsubscribe link; unsubscribing is a button on a page (a mail scanner opening the link cannot unsubscribe anyone). Limits: 1000 people, 3 a day.
- **Analytics** (`tools/analytics.py`): daily counters of searches, results, sold-out nights, room holds, submits and bookings; no identifier of any kind is stored. The funnel is the ratio between the counters.
- **PWA**: manifest, icons (`tools/make_icons.py`), service worker (offline shell; the API is never cached), install button in the footer, offline banner with the properties' phone numbers (cached from the last visit), and a "book again" shortcut that fills the search from the last booking's property, type, guests and nights (kept in the browser, no name or number).
